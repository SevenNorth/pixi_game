# 雷电法王皮卡丘：玩法与技术规划

> 状态：Phaser 阶段零已完成
>
> 更新时间：2026-08-06
>
> 当前基线：Phaser 3.90.x + TypeScript + Vite + DOM HUD

## 1. 项目定位

将当前的 2D 动作小游戏扩展为一款“无限生存 + Roguelite 成长”游戏。

玩家控制皮卡丘在无限世界中移动、探索、躲避障碍物和追踪型怪物，使用攻击击杀怪物并获取经验，通过食物获得临时效果，通过升级和满级后的强化选择构建角色能力，尽可能长时间生存。

## 2. 核心循环

```text
移动探索
  -> 躲避障碍物和怪物
  -> 收集食物，获得临时效果
  -> 攻击并击杀怪物，获得经验
  -> 升级，提升基础生存能力
  -> 满级后通过击杀获得永久强化选择
  -> 怪物持续增强
  -> 血量耗尽，游戏结束
```

## 3. 已确定的玩法方向

### 3.1 无限世界

- 使用无限逻辑世界，不创建无限大的 Canvas。
- 玩家使用世界坐标移动，摄像机跟随玩家。
- 只加载和渲染玩家附近区域。
- 地图建议按区块生成，例如 `512 x 512` 一个区块。
- 远离玩家的对象需要销毁、回收或转为轻量逻辑数据。

### 3.2 障碍物

- 世界中随机生成静态障碍物。
- 障碍物至少影响玩家移动和敌人移动。
- 第一版暂不引入复杂动态陷阱。
- 玩家出生点附近必须保留安全区域。
- 食物和敌人不能生成在明显不可达或不公平的位置。
- 地图随机最好支持种子，以便复现问题和调试。

### 3.3 食物效果

食物从“加分道具”升级为短期战术资源。候选效果包括：

- 恢复血量
- 增加护盾
- 移动速度提升
- 攻击速度提升
- 子弹速度提升
- 子弹伤害提升
- 子弹数量或穿透提升
- 经验获取倍率提升
- 自动拾取或磁铁效果

食物效果具有持续时间，可以和其他不同效果同时存在。

### 3.4 效果叠加

- 不同效果可以并行生效。
- 同一种效果重复获得时，刷新持续时间。
- 是否同时增加层数和强度，需要在实现前最终确定。
- 每种效果需要有最大层数或最大强度限制。
- 食物效果和永久强化使用独立的数据和持有上限。

建议的第一版规则：同类效果增加层数，持续时间重置为完整时长；达到最大层数后不再增加强度，但仍刷新时间。

### 3.5 经验和升级

- 击杀怪物获得经验。
- 经验进入角色经验条。
- 达到阈值后升级。
- 升级增加最大血量，并恢复少量当前血量。
- 升级过程中暂停游戏，避免玩家在选择期间受到攻击。
- 需要处理一次获得大量经验导致连续升级的情况。

### 3.6 血量和护盾

血量和护盾都按“点”计算：

```text
受到伤害
  -> 先扣护盾
  -> 剩余伤害扣当前血量
  -> 血量 <= 0，游戏结束
```

建议模型：

```ts
interface VitalStats {
  hp: number;
  maxHp: number;
  shield: number;
  maxShield: number;
}
```

建议初始规则：护盾是短期防御资源，不快速自动恢复；受伤后提供短暂无敌时间，避免连续碰撞瞬间扣空血量。

### 3.7 等级上限和永久强化

- 角色等级有上限。
- 达到满级后，继续击杀一定数量的怪物可触发强化选择。
- 强化不同于食物效果，默认是永久效果。
- 每次提供若干候选强化，玩家选择一个。
- 永久强化具有持有上限。
- 强化槽位达到上限后，允许用新强化替换已有强化。

候选永久强化：

- 子弹穿透增加
- 子弹数量增加
- 攻击间隔减少
- 移动速度永久提升
- 护盾上限增加
- 受到伤害降低
- 经验获取增加
- 食物持续时间增加

### 3.8 怪物难度成长

怪物难度至少包含三个维度：

- 血量点数随玩家等级或游戏时间提升
- 移动速度随等级或游戏时间提升
- 出现数量增加，生成间隔缩短

建议后续引入“难度预算”而不是单纯堆数量：

```text
ThreatBudget = 基础预算 + 存活时间系数 + 玩家等级系数
```

不同怪物类型消耗不同预算，以便控制整体压力和性能。

## 4. 推荐状态模型

当前状态只有 `playing`、`score` 和 `killed`，无法覆盖新玩法。后续建议统一由可序列化的 `GameState` 保存：

```ts
interface GameState {
  status: 'menu' | 'playing' | 'paused' | 'level-up' | 'game-over';
  elapsedTime: number;

  player: {
    x: number;
    y: number;
    hp: number;
    maxHp: number;
    shield: number;
    maxShield: number;
    level: number;
    experience: number;
    experienceToNext: number;
  };

  foods: FoodState[];
  monsters: MonsterState[];
  bullets: BulletState[];
  obstacles: ObstacleState[];

  foodEffects: EffectInstance[];
  permanentUpgrades: UpgradeInstance[];

  score: number;
  killed: number;
  postMaxLevelKills: number;
}
```

核心原则：模拟状态独立于 Pixi Sprite，渲染对象不能作为游戏状态的唯一来源。

## 5. 推荐运行时边界

```text
InputController
      -> GameSimulation.update(delta)
      -> CollisionSystem
      -> GameState
      -> PixiRenderer.sync(GameState)
      -> HUD / 菜单同步
```

建议的目录方向：

```text
src/
```

## 6. 必须优先解决的技术问题

在新增玩法前，先完成从 PixiJS 到 Phaser 的运行时迁移。迁移不是逐行翻译现有代码，而是在 Phaser 中重新建立场景、输入、时间、摄像机、动画和碰撞边界，同时保持现有玩法行为一致。

### 6.1 Phaser 迁移原则

- 先完整还原当前玩法，再增加新系统。
- 保留现有图片资源和玩法规则，替换 PixiJS 运行时实现。
- 使用 Phaser Scene 管理启动、菜单和游戏生命周期。
- 使用 Phaser Time Event 替代 `setInterval` 和 `Date.now()` 驱动的游戏计时。
- 使用 Arcade Physics 管理玩家、怪物、食物、子弹和障碍物碰撞。
- 使用 Phaser Camera 建立后续无限世界需要的世界坐标和视口边界。
- HUD、菜单和升级选择默认使用 DOM，Canvas 专注于游戏世界。
- 游戏状态和规则保持在独立 simulation 层，不将 Phaser Sprite 作为唯一状态来源。
- 只有在 Phaser 版本完成行为对齐并通过验证后，才删除 PixiJS 依赖和旧运行时代码。

### 6.2 时间系统统一

当前同时使用 Pixi ticker、`setInterval`、动画内部定时器和 `Date.now()`。后续应统一使用 ticker 的 delta 时间，确保暂停、切后台和速度控制行为一致。

### 6.3 资源预加载

现有 Player、Monster、Bullet 在构造函数中异步加载 Sprite。迁移后统一在 Phaser BootScene 中预加载资源、注册精灵动画，再进入游戏场景，避免实体已经开始更新但资源尚未就绪。

### 6.4 碰撞与渲染解耦

碰撞不应长期依赖 `sprite.getBounds()`。应使用逻辑坐标和明确的 hitbox，渲染层只负责将状态显示出来。

### 6.5 输入集中管理

将方向键、攻击、暂停、重启统一映射为 action，后续再扩展 WASD、手柄和移动端输入。

### 6.6 实体生命周期

统一处理实体创建、激活、停用、销毁和 ticker 注册，避免重启后重复监听或残留对象。

### 6.7 响应式视口

无限世界需要明确区分屏幕坐标、摄像机坐标和世界坐标，并处理窗口缩放、横竖屏和移动设备尺寸。

## 9. 验收标准

### 游戏性

- 玩家可以持续移动和探索，不会因为固定画布边界被迫停止。
- 障碍物会影响路线，但不会造成明显不公平的出生或封路。
- 食物效果可以同时存在，并按规则叠加或刷新。
- 受到伤害时先消耗护盾，再消耗血量。
- 击杀怪物可以获得经验，升级后有明确的生存收益。
- 满级后仍然存在可选择的长期成长。
- 怪物难度提升具有可感知但可应对的节奏。

### 技术性

- 暂停时所有游戏时间、生成器和动画均暂停。
- 重启后不存在重复 ticker、定时器或键盘监听。
- 远离玩家的世界对象会被回收，不会无限增长。
- 游戏状态可以独立序列化，渲染对象销毁不会破坏核心状态。
- 桌面和移动尺寸下 HUD、Canvas 和输入不互相遮挡。

## 10. 推荐开发顺序

已决定现在迁移到 Phaser。推荐按以下顺序实施：

1. 在独立分支建立 Phaser 运行时骨架。
2. 完整对齐当前 PixiJS 版本的移动、攻击、怪物、食物、计分、暂停和重启行为。
3. 通过构建和浏览器测试后移除 PixiJS 运行时代码。
4. 抽离 `GameState`、`GameSimulation`、输入 action 和实体生命周期。
5. 实现血量、护盾和碰撞伤害。
6. 实现经验和升级。
7. 实现食物效果及叠加规则。
8. 实现摄像机、世界坐标、区块和障碍物。
9. 实现满级永久强化和替换。
10. 最后调节怪物难度、生成预算和性能。

## 11. Phaser 迁移验收标准

- 现有图片资源可以正常加载，不依赖远程地址。
- 玩家四方向移动和动画方向正确。
- 空格攻击方向、出生位置和冷却符合当前手感。
- 怪物保持追踪行为，碰撞能够结束当前版本的游戏。
- 食物能够随机出现、超时消失并增加分数。
- 击杀数、分数、开始、暂停和游戏结束 UI 正常工作。
- 暂停时 Phaser 时间事件、物理、动画和生成逻辑都停止推进。
- 重启后不存在重复监听、重复生成器或残留实体。
- 窗口尺寸变化后 Canvas 和 DOM HUD 不重叠、不溢出。
- `yarn build` 成功，浏览器控制台无运行时错误。
- 达到以上条件后，删除 PixiJS 依赖和旧运行时代码。
